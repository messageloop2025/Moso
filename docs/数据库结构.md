# 毛竹 数据库结构

基于 `database/models.py` 中的 SCHEMA_SQL 与迁移逻辑整理。数据库为 **SQLite**，单文件。

## 版本与升级（必读）

- **代码不兼容老版本数据库。** 系统启动时会检查 `schema_version` 表，并按顺序执行 `database/migrations/` 下的升级脚本，将数据库升级到当前代码所要求的版本。
- **项目规则**：任何修改数据库结构的操作（增/删/改表、列、索引等）都将引起数据库版本增加，并**必须**在 `database/migrations/` 下新增对应编号的升级脚本。不得在业务代码中为兼容老库写分支；老库通过启动时执行升级脚本升级。详见 `database/migrations/README.md`。

### 1.1 运行时连接参数（非迁移 DDL）

启动时在 `database/models.py` 的 `apply_sqlite_concurrency_settings` 中设置，利于**多用户并发**（见 [并发与扩展.md](并发与扩展.md)）：

- `PRAGMA busy_timeout` — 环境变量 `EDGEOPS_SQLITE_BUSY_TIMEOUT_MS`（默认 5000）
- `PRAGMA journal_mode=WAL` — 可用 `EDGEOPS_SQLITE_WAL=false` 关闭
- `PRAGMA synchronous=NORMAL`
- `PRAGMA foreign_keys=ON`

### 2.13.1 ai_host_prompts（主机维度 AI 提示词表）

按「用户 × 主机」存储该主机的「主机级 AI 提示词」：描述该主机独有的**规则 / 能力 / 工具链 / 配置**。按用户独立存储，主机分享给其它用户时提示词不共用。在主机维度会话中会被自动注入 system 提示词，AI 可据此了解该主机的特殊能力与约束。

| 列名 | 类型 | 说明 |
|------|------|------|
| host_id | INTEGER NOT NULL FK → hosts(id) ON DELETE CASCADE | 主机 |
| user_id | INTEGER NOT NULL FK → users(id) ON DELETE CASCADE | 用户 |
| content | TEXT | 提示词内容（可 Markdown） |
| updated_at | DATETIME | 更新时间 |
| PRIMARY KEY (host_id, user_id) | | 联合主键 |

**索引**：`idx_ai_host_prompts_user` ON user_id

**content 中的自动画像哨兵块**（2026-04 起）：
`content` 支持由 AI 技能 `probe_host_capabilities` 自动写入的一段**主机能力画像** Markdown，用哨兵包裹：

```
<!-- EDGEOPS:HOST_PROFILE v1 -->
## 主机能力画像（自动采集于 <ISO 时间>）
### 基础 / 硬件 / 云与基础设施 CLI / AI 代理 CLI / 语言运行时 / DevOps / 安全 / 渗透 / 数据库客户端
...
<!-- /EDGEOPS:HOST_PROFILE v1 -->
```

合并策略：**只替换哨兵内部**，哨兵之外用户或 AI 手写的规则、注意事项等保持不变。再次调用 `probe_host_capabilities` 默认 24 小时内有画像则复用缓存，`refresh=true` 强制重探。

**相关 API / Skills**：
- `GET  /api/ai/hosts/{host_id}/prompt` 读取
- `PUT  /api/ai/hosts/{host_id}/prompt` 覆盖
- `POST /api/ai/hosts/{host_id}/prompt/summarize?action=replace|append` 由 AI 总结
- AI 技能：`probe_host_capabilities` / `get_host_capabilities`（主机能力画像，写入/读取哨兵块）

**相关 AI 工具**：`get_host_prompt` / `update_host_prompt` / `append_host_prompt` / `search_hosts_by_prompt`（按关键字 + 可选分组/标签搜索具备某能力的主机）。

### 2.13.2 ai_workflow_templates（AI 编排工作流模板）

保存 `delegate_chain` 的完整 payload 供复用。典型场景：用户跑完一条复杂链（比如"A 机改代码 → B 机跑测试 → C 机部署"）后说「这条以后我还要跑」，AI 就把原 payload 存进来；之后任意时刻说「跑一次 daily-deploy」即可通过 `run_workflow_template` 拉起。

### 2.35 user_feedback（系统内用户反馈，迁移 015）

| updated_at | DATETIME DEFAULT CURRENT_TIMESTAMP | 最近修改/状态变更 |

## 2.X 用户删除级联清理（重要）

删除用户（管理员在「用户管理」点击「删除」或用户在「系统设置」里点击「注销账户」）时，必须**递归**清除一切与该用户相关的数据，包括因其主机被其他用户访问而形成的数据。由 `api/users.py` 的 `delete_user_with_cascade` 统一实现，分三步：

删除管理员的额外规则：管理员不能删除自己；管理员账户数量大于 1 时，允许一位管理员删除另一位管理员；不允许删除最后一个管理员账户。

**A. 清理该用户所创建的主机，以及这些主机在「任何用户侧」形成的每用户数据（先清子表，再删主机）**

- `ai_chat_messages`（通过 `ai_chat_sessions.host_id IN (...)` 关联）
- `ai_chat_sessions.host_id IN (...)` — **所有用户**的与这些主机相关的聊天会话（含被分享方的聊天记录）
- `ai_host_knowledge.host_id IN (...)` — 所有用户在这些主机上写入的个人知识
- `ai_host_prompts.host_id IN (...)` — 所有用户在这些主机上写入的会话/主机级提示词
- `host_shares.host_id IN (...)` — 这些主机的分享关系（同时从被分享方账号里消失）
- `host_user_tags.host_id IN (...)` — 所有用户给这些主机打的个人标签
- `host_group_members.host_id IN (...)` — 分组成员关系
- `batch_operation_details.host_id IN (...)` — 任意用户批量操作里涉及这些主机的明细
- `operation_logs.host_id IN (...)` — 所有用户操作这些主机的日志
- `ssh_channels.host_id IN (...)` — 所有用户到这些主机的 SSH 通道
- 最后 `DELETE FROM hosts WHERE id IN (...)`

**B. 清理该用户自身的每用户数据（`user_id = <user_id>` 或 `created_by = <user_id>`）**

- AI 对话：`ai_chat_sessions` + `ai_chat_messages`（含全局、本机管理、任意主机下的会话）
- 作为被分享方在他人主机上的知识/提示词：`ai_host_knowledge` / `ai_host_prompts`
- 个人标签与关联：`host_tags`（created_by）、`host_user_tags`（user_id）
- 分享记录：`host_shares.shared_with_user_id = ?` **和** `host_shares.owner_user_id = ?`
- 主机分组：`host_groups`（及其 `host_group_members`）
- 凭证：`credentials.created_by = ?`
- 自动化：`triggered_tasks` / `triggered_task_runs` / `triggered_task_run_messages` / `triggered_task_expose`；`scheduled_tasks` / `scheduled_task_runs` / `scheduled_task_run_messages`
- 通道与批量：`ssh_channels.user_id = ?`；`batch_operations.created_by = ?` 及其 `batch_operation_details`
- 本机：`local_shell_sessions` / `local_shell_logs`
- 个人配置：`user_ai_config`（含 `active_profile_id`）、**`user_ai_model_profiles`**、`user_system_ai_usage`、`user_mail_config`、`api_tokens`、**`user_mcp_servers`**、**`user_skills`**
- 审计/事件：`user_login_events`、`operation_logs.user_id = ?`、`server_maintenance_history.created_by = ?`
- 邮箱验证/重置：`email_verification_codes`、`password_reset_tokens`
- 反馈与留言板：
  - `user_feedback_replies.admin_user_id = ?` — 该用户作为管理员写过的回复
  - `user_feedback.user_id = ?` — 该用户提交的所有反馈（连同其下 `user_feedback_replies.feedback_id` 因 `ON DELETE CASCADE` 一起删）
  - `anonymous_messages.author_user_id = ?` — **不删留言/回复内容本身**，仅把作者引用置 `NULL`（保留登录页留言板上下文）
- **`best_practices` 例外**：**不删内容，仅把 `created_by` 置 NULL**——共享知识库不因个人账户销毁而丢失，仅移除归属。

**C. 最后删除用户本行 + 清理 `web/fs/<safe_username>/` 下的整个工作目录**

实现要点：

- 整个过程在同一个 SQLite 事务里完成（`delete_user_with_cascade` 内只执行 `DELETE/UPDATE`，由外层 `delete_user` / `delete_my_account` 统一 `commit()`）；任何一步失败将整个事务回滚。
- 大 IN 列表按 500 一批分块（`_chunked_in_delete`），避免触发 SQLite 参数上限。
- 对部分老库缺失的可选表（如 `ssh_channels`、`host_shares`、`api_tokens`、`host_tags`、`user_login_events`、`best_practices`）用 `_table_exists` 做保护。
- 管理员账户被禁止自助注销（`POST /api/users/me/delete` 对管理员返回 403），以免误删最后一个管理员；需由另一位管理员在「用户管理」里删除。

## 3. 迁移说明（兼容旧库）

以下列/表可能由迁移逻辑在首次启动时补充，而非全部写在 SCHEMA_SQL 中：

- **users.email**、**users.failed_login_attempts**、**users.locked_until**：若不存在则由 `_migrate_users_login_lockout` 添加（邮件找回密码与登录锁定）。
- **password_reset_tokens**：若表不存在则由 `_migrate_password_reset_tokens` 创建。
- **local_shell_sessions**、**local_shell_logs**：若表不存在则由 `_migrate_local_shell_tables` 创建（本机管理）。
- **hosts.credential_id**：若不存在则 ALTER TABLE 添加。
- **hosts.host_type**、**hosts.host_version**：若不存在则 ALTER TABLE 添加（默认 '未知'），用于保存检测到的操作系统类型与版本。
- **host_groups.parent_id**：若不存在则 ALTER TABLE 添加。
- **ai_chat_sessions.host_id**：若不存在则 ALTER TABLE 添加；并创建 `idx_ai_sessions_host`。
- **ai_chat_sessions.low_interaction_mode**：若不存在则 ALTER TABLE 添加（默认 `'false'`，会话级低交互开关）。
- **operation_logs.source**：若不存在则 ALTER TABLE 添加。
- **ai_host_knowledge**、**best_practices**：若表不存在则 CREATE TABLE。
- **batch_operations**、**batch_operation_details**：若表不存在则 CREATE TABLE（批量操作）。
- **host_shares**：由迁移 **009_host_shares.py** 创建（主机分享关系，支持撤销与审计）。
- **user_ai_config**：若表不存在则 CREATE TABLE（每用户 AI 配置）；由 `_migrate_user_ai_config` 创建。
- **user_ai_config.provider**：若列不存在则由 `_migrate_user_ai_config_provider` 添加（AI 源类型，空=自动探测）。
- **user_ai_model_profiles**、**user_ai_config.active_profile_id**：由迁移 **031** / `_migrate_user_ai_model_profiles` 创建；旧 `user_ai_config` 单行自动迁移为「默认配置」Profile。
- **user_system_ai_usage**：若表不存在则由 `_migrate_user_system_ai_usage` 创建（未配置 KEY 用户使用系统 KEY 的调用次数统计）。
- **hosts.username** 若为旧版 NOT NULL，会通过重建表改为可空。
- **settings**：`_migrate_settings_smtp_site_url` 确保存在 site_url、smtp_* 等键（INSERT OR IGNORE）。
- **`database/migrations/` 编号脚本**：如 **004** 为 `scheduled_tasks.enabled`、**006** 为 `hosts.aliases` / `hosts.remark`、**007** 为 `user_mail_config` 表与 `scheduled_tasks.notify_email_to`、**015** 为反馈与登录留言板、**026** 为 `mcp_agent_tasks` / `mcp_agent_task_controls`、**027** 为 `user_mcp_servers`、**028** 为 `chat_scope_*`、**029** 为 `users.skills_enabled` + `user_skills`、**030** 为移除 `offline_request_*` 表及相关 settings 键、**031** 为 `user_ai_model_profiles` + `active_profile_id`；当前目标 **schema_version=32**（`database/bundles/fresh_install.sql`）；启动时按 `schema_version` 顺序执行，直至与代码目标版本一致。

实现见 `database/models.py` 中的 `_migrate_*` 与 `init_db()` 调用顺序。

**从 0.2.x 升级**：新版本在应用启动时（lifespan）会统一执行 `init_db()`，旧库会自动补全缺失表/列（如 `user_system_ai_usage`）。若你曾用多 worker 或 `uvicorn app:app` 等方式启动导致当时未跑迁移，可**手动执行一次迁移**（在项目根目录）：

```bash
python scripts/migrate_db.py
```

或指定数据库路径：`EDGEOPS_DB=/path/to/edgeops.db python scripts/migrate_db.py`。执行后重启应用即可。

先配置 AI 模型——
这是 Moso 唯一且必须的第一步

没有 AI 模型，Moso 不具备实质运维能力。 配置好大模型后，所有操作——添加主机、管理凭证、跑批量、排障、建任务、写提示词、审计日志—— 都可以直接在 AI 聊天里用自然语言完成。AI 辅助就是本系统的核心操作入口，从这里开始一切操作。

步骤 1｜必须
🤖

选择并配置一个大模型

三选一即可：
· 阿里云 DashScope（qwen 系列，国内推荐）
· Ollama 本地（数据不出内网）
· OpenAI / 任意兼容接口
管理员可在「全局设置」写默认；每个用户也能在「我的 AI 配置」里填 Base URL + API Key + Model。未填自有 Key 时暂用系统共享 Key（默认 2000 次配额，可配置）；配置了自己的 KEY 后 解除次数限制，不再计数。

步骤 2｜从这里开始
💬

打开 AI 助手，一切从对话开始

登录后顶部有"AI 助手"入口。你不需要先学界面——直接用中文说：
· "添加一台 10.0.0.12 的主机并保存 ssh 密钥"
· "在线上 tag 的机器上批量升级 nginx"
· "每天凌晨 3 点清一遍 /tmp 超过 7 天的文件"
AI 会自动调用 165+ 种内部工具完成上述动作，并把每一步都写入操作日志。

步骤 3｜越用越聪明
🧠

让 AI 沉淀"这台机器的规则"

运维时告诉 AI："这台机用 zsh + brew、数据在 /data、禁止在生产时段重启 nginx"—— AI 会自动写进主机级提示词（按用户×主机独立保存）， 之后进入该主机的会话会自动加载这份规则，不再重复询问。 再配合按钮式选择题，AI 可主动发起"确认 / 取消 / 危险按钮"让你一点即答。

⚠️ 没配模型 = 什么都做不了。 配好模型、打开 AI 助手，所有日常运维操作都可以在聊天里完成。

AI 能力

不是"生成一段脚本给你 copy 执行"，而是直接动手的 Agent

Moso 的 AI 助手通过 Function Calling 操作真实资源：SSH 命令、SFTP 推送、主机知识、会话提示词、批量任务、SMTP 发信、本机 shell 与进程管理……全部可审计。

"帮我找到一台装了 gh cli 的机器，拉一下 PR 列表"

AI 会先调用 search_hosts_by_prompt 按"主机级提示词"做关键字+正则搜索， 再 connect_terminal 到命中主机，执行 gh pr list，并把结果呈现回聊天区。

  • 主机级提示词：每台主机可写工具链、目录约定、规则与禁忌（Markdown）；按当前用户独立，不受主机分享影响。
  • 会话级提示词：当前聊天单独生效，可让 AI 临时遵循某些流程或偏好。
  • 主机知识库：保存账户/密码/Token 等敏感信息，与提示词隔离，仅 AI 在需要时按主机调用。
  • 跨主机检索：search_hosts_by_prompt(query, group_id?, tag_ids?, regex?) 在用户可访问主机中按能力描述做关键字/正则检索。
  • 多轮 Agent：工具结果回传后 AI 继续决策；支持自动批准、最大步数控制、上下文自动压缩保护。

165+ 工具，一套即覆盖日常运维 90% 场景

AI 不再"建议你怎么做"，而是直接以最小权限调用底层工具完成任务；所有调用都写入操作日志。

  • 终端协同：AI 读写当前用户 SSH 终端缓冲区，支持多控制台切换（主机详情 / AI 助手）。
  • SSH Channel：长连接 TTY 通道，按会话或任务隔离；按行号/字符数读取，适合交互式命令。
  • 本机管理：管理员可让 AI 在 Moso 宿主机上执行 shell、Python 脚本、管理子进程、读写文件。
  • 多主机中继：跨主机文件直接中继，免去"先拉回本地再推过去"。
  • 系统共享 Key 配额 + 自有 KEY：用户未配置自有 Key 时使用系统共享 Key（默认 2000 次配额），用尽后 AI 会提示；配置自有 KEY 即 解除次数限制；管理员可清零任意用户的共享 Key 计数或为其写入系统默认配置。
多主机协同

把"开发 → 发布 → 运维 → 反馈"
一条消息串起来，跨多台电脑自动联动

Moso 天然面向多机场景——同一个 AI 会话可以同时驾驭 N 台主机。 开发机、构建机、测试机、生产机、监控机各司其职，由 AI 用 delegate_chain 一次性声明执行链、按主机鉴权、按步骤推送实时进度，跑一次满意还能存成 workflow_template 反复跑。 你不再需要"先 SSH 到 A 机做 X、再 SSH 到 B 机做 Y"——一句话，一条链，全机房协同。

AI 会画像 4 台主机 → 生成一条 8 步 `delegate_chain` → 弹按钮让你一次性确认整条链 → 流式进度边跑边推 → 跑完说"要不要把这条存成 release-v2 模板？" 
# AI 生成的 delegate_chain（跨 4 台主机）
tool_call: delegate_chain
  confirmed: true
  steps:
    #1 delegate  @dev-01     agent=cursor-agent
        task=Implement jwt-login per SPEC.md
    #2 ssh       @dev-01
        cmd=pytest -q                        # 开发自测
    #3 ssh       @build-02   when=on_success
        cmd=docker build -t app:v2.3.0 .
    #4 ssh       @build-02   when=on_success
        cmd=docker save app:v2.3.0 | \
             ssh prod-03 'docker load'       # 跨机中继
    #5 ssh       @prod-03    when=on_success
        cmd=systemctl restart app
    #6 sleep     5s                              # 等服务起稳
    #7 ssh       @monitor-04
        cmd=curl -s prom/api/query?p99
    #8 delegate_to_edgeops_ai   when=always
        system_prompt="你是运维周报撰写员..."
        task="按 {prev_stdout} 写中文周报"
    #9 tool      send_email  to=oncall@co.com

🧭

按主机画像选型

下单前 AI 自动跑 probe_host_capabilities，按每台主机真实的 OS / 硬件 / 已装 CLI 挑工具——Kali 上用 nmap，GPU 机上跑训练，有 kubectl 的跑 k8s。

🧩

每步独立鉴权

delegate_chain 的每一步可以独立 host_id；执行前对所有涉及主机做访问 / 凭证 / 能力预检；执行中按主机分别审计；权限越界直接拒绝整条链。

📡

流式进度同屏

跨 10 台机、每台跑几十秒的链也不再"黑盒等待"——每一步的 stdout / stderr / 子 AI 输出都通过 SSE 实时推到工具卡底下，随时看到卡在哪一环。

🧱

跑一次，存下来再跑

满意的跨机链 → save_workflow_template，变量写成 ${var}；以后 run_workflow_template("release-v2", branch="v2.4") 一句话复现；组织内可共享。

🕰️

丢进定时任务裸跑

把整条 delegate_chain / 模板丢给定时或触发任务——task scope 下自动视为已授权；凌晨无人值守时按机房规模跑几十步的自愈流水线。

🧠

子 AI 做汇总 / 审查

delegate_to_edgeops_ai 起一个内部子 AI 写报告、review 脚本、聚合多路分析——独立上下文、独立 system_prompt、硬限制递归深度=2，不会"套娃失控"。

📮

跨机中继 & 反馈闭环

文件 transfer_file_between_hosts / relay_file_between_hosts 直接机对机，免去本地绕一圈；结果顺手 send_email 给 oncall，闭环到反馈阶段。

🧾

全量操作日志

跨 N 台主机的每一步都会在对应主机的 audit_log / 任务日志 .edgeops/task/ 下各留一条，谁、何时、在哪台、执行了啥、退出码多少，一目了然可回溯。

典型多机联动场景

🚀

CI/CD 流水线

开发机 agent 改代码 → 构建机出 docker 镜像 → 测试机 pytest → 生产机热更新 → 监控机巡检 P99。一条链写完，失败自动回滚。

🛡️

安全渗透 + 复盘

Kali 机跑 nmap / nikto → 目标机拉日志 → Moso 子 AI 把两边输出合成中文漏洞报告，邮件送安全团队。

🗄️

数据库跨机备份

主库 mysqldump → rsync 到备份机 → 备份机算 SHA256 校验 → 监控机注册本次备份元数据 → SMTP 发报告。

🧯

线上故障自愈

监控机检测到 5xx 激增 → 触发任务调 run_workflow_template("hotfix") → 构建机打 patch → 生产机灰度 → 子 AI 写事故报告。

🏭

机房扩缩容

控制机 terraform 申请新节点 → ansible 机刷基线 → 新节点自己 probe 能力回传 → 负载均衡机加权。全程不用登录跳板机。

🧪

AI + AI 接力

dev-01 的 cursor-agent 改代码 → test-02 的 aider 补单测 → review-03 的 opencode 做 PR review → 全部失败转给 Moso 内部子 AI 人工跟进。

自动化编排

把 AI 的能力延续到没人值守的时刻

触发任务是"由条件/他人触发的 AI 任务"；定时任务用 cron 驱动 AI 任务；两者可互相触发，形成事件驱动的运维编排。

触发任务

为一段 AI 指令命名 + 写"触发条件"描述，AI 或其他任务可按需触发。

  • 可被其他任务调用：任务间可形成条件分支与调用链。
  • 暴露接口：可配置为供定时任务发现（triggered_task_list_exposed）。
  • 会话式历史：每次运行保留完整聊天式运行历史，方便复盘。
  • 按用户：每用户独立的触发任务清单，管理员审计。

定时任务

经典 5 段 cron，加 enabled 开关、notify_email_to 收件人、run-now 立即执行。

  • SMTP 邮件通知：执行完成后以任务所属用户个人 SMTP 发摘要。
  • 立即执行：不等 cron 也可 scheduled_task_run_now 一键跑。
  • 执行互斥：同一任务 cron 触发与立即执行互斥，避免并发冲突。
  • 运行历史：按 run_id 保留每次运行的会话消息，失败可追查。

常见问题

你可能想先问的几个

Moso 与普通 SSH Web Shell 有什么不同？

Moso 不仅是 Web 终端：它把 AI 助手作为一等公民融入其中 —— AI 通过 Function Calling 直接操作主机、文件、任务、配置； 同时保留"主机树 + 凭证分离 + 多用户隔离 + 全量日志"的企业级运维管理结构。 你可以只用它的终端面板，也可以让 AI 代替你完成 80% 的操作而你只做审批与复盘。

⚠️ 必须先配置 AI 模型吗？可不可以"纯终端"不用 AI？

必须先配置大模型。Moso 把 AI 当成主入口来设计——没有模型时，"AI 助手 / 主机 AI 运维 / 触发任务 / 定时任务 / 本机管理 AI"等绝大部分核心能力都无法工作。 兼容三大类接口：阿里云 DashScope（compatible-mode） / Ollama 本地 / OpenAI 原生或兼容。 每个用户都能单独配置 Base URL、Key、模型；也可以继承管理员写好的系统默认配置。 未配置自有 Key 的用户默认使用系统共享 Key，并有 2000 次配额（可配置）；每轮 AI 首条回复会提示已用/剩余；用尽后引导用户配置自有模型或联系管理员重置计数 / 写入系统默认配置。管理员可随时清零共享 Key 计数。

"主机级 AI 提示词"和"主机知识库"有什么区别？

主机级提示词：写主机独有的规则、已装工具链、目录约定、禁忌等 —— 用于让 AI 更清楚"在这台机器上能做什么、该怎么做"，支持跨主机按能力检索。 主机知识库：写账户、密码、Token 等敏感信息 —— AI 只在真正需要时按主机调用，不用于跨主机搜索。 两者均按用户 × 主机独立保存，主机分享给他人时不会共用。

AI 会不会擅自执行危险命令？

执行类操作必须经 tool_call 完成，全量写入操作日志；用户可开启「自动同意」或逐条审批。 生产环境建议关闭自动批准高风险工具调用，并在主机级提示词中写明禁止项与变更窗口；需要人工确认的操作保持逐条审批。

可以本地部署吗？数据会被上传吗？

完全可以本地化：SQLite 单文件数据库，所有数据本地保存。如果你使用 Ollama 模型，连模型推理也不出本地。 如果使用云端 LLM，仅将聊天上下文发给你配置的大模型服务商，不会上传到第三方。

一台 Moso 能服务多少台主机？

Moso 本身是协作工具，连接数主要受内存与 SSH 会话上限约束；数据层用 WAL SQLite 应付中小规模团队绰绰有余。 大型团队可扩展到多进程（Linux 下 EDGEOPS_WORKERS>1），但由于内置调度器与 SQLite 写并发特性，推荐单进程 + 容器副本拓扑。

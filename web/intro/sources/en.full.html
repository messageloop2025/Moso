On first setup · read this

Configure an AI model first—
the one and only required first step in Moso

Without an AI model, Moso does not deliver real operations capabilities. After the model is set up, all actions—adding hosts, managing credentials, running batches, troubleshooting, creating tasks, writing prompts, auditing logs— can be done in AI chat in natural language. AI assistance is the core control surface of this system; you start all operations from here.

Step 1 · required
🤖

Choose and configure a large language model

One of the following is enough:
· Alibaba Cloud DashScope (Qwen family—common in China)
· Ollama on your network (data does not leave the intranet)
· OpenAI or any compatible API
Admins can write defaults in global settings; each user can set Base URL + API key + model in My AI config. Until you add your own key, a shared system key is used (default 2000 calls, configurable); after you configure your own key, the usage cap is removed and counting stops.

Step 2 · start from here
💬

Open the AI assistant—everything starts in the conversation

After login, the AI assistant is in the header. You do not need to learn the UI first—just say, for example:
· “Add a host 10.0.0.12 and save the SSH private key”
· “Batch-upgrade nginx on machines with the online tag”
· “Every day at 3:00 a.m. delete /tmp files older than 7 days”
The model automatically uses 100+ internal tools, and every step is written to the operation log.

Step 3 · gets smarter with use
🧠

Let the AI keep “this machine’s rules”

As you work, tell the AI: “This machine uses zsh + Homebrew, data is under /data, do not restart nginx during business hours”— the AI will write that into the per-host prompt (saved per user × host), and later sessions on that host load the rules so it does not ask the same things again. Together with clickable choice cards, the model can show confirm / cancel / danger-style buttons you answer in one click.

⚠️ No model configured = nothing to do. Set up the model, open the AI assistant, and you can run day-to-day operations entirely from chat.

AI

Not “I’ll generate a script for you to copy and run”—an agent that acts directly

The Moso AI assistant uses function calling to touch real resources: SSH commands, SFTP push, host knowledge, session prompts, batch jobs, SMTP mail, local shell and process management … all audited.

“Find a host with the gh CLI installed, and pull the PR list”

The AI first calls search_hosts_by_prompt to search the per-host prompt with keyword + regex, then connect_terminal to a matching host, runs gh pr list, and shows the result in chat.

  • Per-host prompt: each host can list toolchain, path conventions, rules, and taboos in Markdown; scoped to the current user and not affected by host sharing.
  • Session prompt: applies to this chat only, so the model can follow a given flow or preference temporarily.
  • Host knowledge base: stores accounts, passwords, tokens, etc.; isolated from the prompt, only retrieved per host when the AI really needs it.
  • Cross-host search: search_hosts_by_prompt(query, group_id?, tag_ids?, regex?) does keyword/regex search over the hosts you can access, by capability text.
  • Multi-round agent: after a tool result returns, the model keeps deciding; auto-approve, max steps, and context compression to protect limits.
  • Personal MCP (/mcp-servers): attach third-party MCP tools to web/host/integration AI; JSON import/export.
  • Personal Agent Skills (/skills, admin toggle): Cursor-style SKILL.md, progressive disclosure by default; create/import/export in chat or UI.

100+ tools—one set covers roughly 90% of day-to-day operations

The model does not just “suggest what to do”—it calls the underlying tools with least privilege to finish the job; every call is in the operation log.

  • Terminal in sync: the model reads and writes the current user’s SSH terminal buffer and can switch between consoles (host screen / AI assistant).
  • SSH channel: a long-lived TTY channel, isolated by session or task; read by line/character count, suited to interactive commands.
  • Local host: administrators can have the model run shell, Python scripts, child processes, and file access on the Moso host.
  • Multi-host relay: relay files directly between machines—no “pull to local then push” hop.
  • System shared key quota + your own key: if you have not configured a personal key, a system shared key is used (default 2000 uses); when it runs out, the model prompts; your own key lifts the cap. Admins can clear shared-key counts for any user or apply system default config.
Multi-host

From develop → release → operate → feedback
in one message, across many machines

Moso is built for many hosts—one AI session can drive N machines at once. Dev, build, test, production, and monitoring each do their part; the model can build a delegate_chain in one go, check access per host, stream progress for each step, and—when a run looks good—save a workflow_template to re-use. No more “SSH to A, do X, then SSH to B, do Y” by hand—one request, one chain, the whole environment stays in step.

🧭

Choose from host profile

Before ordering work, the AI runs probe_host_capabilities and picks tools from each host’s real OS, hardware, and CLIs—nmap on Kali, training on GPU machines, k8s where kubectl exists.

🧩

Auth every step on its own

Each delegate_chain step can have its own host_id; before run, we preflight access, credentials, and skills; while running, audit per host; if permissions fail, the whole chain is rejected.

📡

Streamed progress on one screen

With ten machines and long steps you are not stuck in a black box—each step’s stdout, stderr, and sub-AI output is pushed with SSE under the tool card, so you always see the bottleneck.

🧱

Run once, then save and re-run

A cross-host chain you like → save_workflow_template with ${var} variables; next time run_workflow_template("release-v2", branch="v2.4") in one line—sharable inside the org.

🕰️

Drop it into a schedule as-is

Put a full delegate_chain or template into a scheduled or triggered job—the task scope is treated as pre-authorized; at night with nobody online, a self-heal chain can run dozens of steps across the hall.

🧠

Sub-AI to summarize and review

delegate_to_edgeops_ai spawns an inner sub-AI for reports, script review, or bringing many analyses together—its own context and system prompt, max recursion depth 2 so it does not “nest out of control.”

📮

Cross-host relay & closed feedback

Files: transfer_file_between_hosts / relay_file_between_hosts are machine to machine, no detour through your laptop; send_email to oncall closes the feedback loop.

🧾

Full operation log

Each step on N hosts writes one line in that host’s audit_log and task log under .edgeops/task/—who, when, on which host, what ran, exit code—fully traceable.

Typical cross-host collaboration scenarios

🚀

CI/CD pipeline

Dev machine agent changes code → build host produces a Docker image → test host runs pytest → production hot-reload → monitor checks P99. One chain, automatic rollback on failure.

🛡️

Security testing and review

Kali host runs nmap / nikto → target host pulls logs → Moso sub-AI composes a Chinese vulnerability report, emailed to the security team.

🗄️

Cross-host DB backup

Primary mysqldump → rsync to backup host → backup host checks SHA256 → monitor registers this backup’s metadata → SMTP summary.

🧯

On-call self-heal

Monitor host sees a surge in 5xx → a triggered job calls run_workflow_template("hotfix") → build host makes a patch → production canary → sub-AI writes the incident report.

🏭

Datacenter scale-out

Control host with terraform, ansible host for baseline, new nodes self-report capabilities, load balancer reweights—no need to log into a jump host.

🧪

AI hands off to AI

cursor-agent on dev-01 changes code → aider on test-02 adds unit tests → opencode on review-03 does PR review → if it all fails, an Moso inner sub-AI takes over for human follow-up.

Security & scope

A clear permission model: everyone knows what they can see

Every sensitive action is bounded: normal users only see their own; admins can audit the whole; when you share a host, prompts and knowledge do not mix; SMTP and model keys are per person.

🔐

JWT + captcha

Sign-in and sign-up use a simple a+b style math captcha; after too many failures the account is locked, unlock by email; JWT defaults to 24 hours.

👤

User data separation

Operation logs, host prompts, local file area, model config, SMTP, sessions, and messages are all strictly under user_id.

🪢

Host sharing does not mix profiles

You can share a host with someone else, but the per-host prompt and group stay in the receiver’s own namespace.

⚖️

sudo policy

Try passwordless sudo first; only when the terminal really asks for a password, use host knowledge or ask the user and store it as suitable.

📋

Full operation log

UI, model tool calls, sharing, and task triggers are all written to storage; admins can filter by user or host, end users only see their rows.

🪪

API token

Users can issue dedicated API tokens for program access, revocable in personal settings, independent of the sign-in session.

Automation & orchestration

Carry the model’s skills into the hours with nobody at the desk

Triggered jobs are “model jobs someone or something else fires”; scheduled jobs are cron driving model work; the two can call each other to build event-driven operations.

Triggered task

Name a model instruction and write a “when to fire” description; the model or another job can run it on demand.

  • Callable from other jobs: jobs can branch and call each other.
  • Exposed to discovery: you can make it listable to scheduled jobs (triggered_task_list_exposed).
  • Chat-style run history: each run keeps a full chat-style trace for postmortems.
  • Per user: every user has their own triggered list; admins can review.

Scheduled task

Classic five-field cron, plus an on/off switch, notify_email_to, and run-now to execute immediately.

  • SMTP email: on completion, the job owner’s personal SMTP can send a summary.
  • Run now: you can still call scheduled_task_run_now and not wait for cron.
  • Exclusion: cron and run-now for the same job exclude each other to avoid clashing.
  • Run history: each run’s messages are kept by run_id so you can track failures.

Common questions

A few things you may want to ask first

How is Moso different from a web SSH client?

Moso is not only a web terminal: the AI is a first-class citizen—function calling drives hosts, files, jobs, and config. You still get a host tree, separate credentials, multi-user isolation, and full operation logging. You can use only the terminal, or you can have the model do about 80% of the work for you with you approving and reviewing.

⚠️ Do I have to configure an AI model? Can I use “terminal only”?

Yes, you need a model. Moso is built around AI as the main entry—without a model, the AI assistant, per-host AI, triggered tasks, scheduled tasks, and local-host AI will not work. Three API styles: Alibaba DashScope (compatible-mode) / Ollama local / OpenAI native or compatible. Each user sets Base URL, key, and model, or inherits admin defaults. Without your own key, a shared system key applies with a 2000-call quota (configurable); the first reply each round shows usage; when exhausted, configure your own key or ask an admin to reset or apply system defaults. Admins can clear shared-key counts anytime.

“Per-host AI prompts” vs “host knowledge”—what is the difference?

Per-host prompts: rules, installed tools, paths, and taboos—so the AI knows what to do on that machine; searchable across hosts by capability. Host knowledge: accounts, passwords, tokens—used only per host when needed, not for cross-host search. Both are stored per user × host and are not shared when you share a host with someone else.

Can the AI run dangerous commands on its own?

Actions require tool_call and are logged. You can enable auto-approve or review each call. In production, avoid auto-approving risky tools; put forbidden actions and change windows in per-host prompts; keep human confirmation where needed.

Can I deploy on-prem? Is data uploaded?

Yes: SQLite in one file, all data local. With Ollama, inference can stay on your network too. With a cloud LLM, only the chat context goes to the provider you configured—nothing extra to a third party.

How many hosts can one Moso serve?

Moso is a collaboration hub; connections are limited mainly by memory and SSH sessions. WAL SQLite is enough for most small and mid teams. Larger deployments can use multiple workers on Linux (EDGEOPS_WORKERS>1); with the built-in scheduler and SQLite write patterns, a single process plus container replicas is usually recommended.

How do I start?

① Register and sign in (email optional + captcha) → ② ⚠️ The most important step: in “System settings → My AI config”, fill in Base URL / key / model—without this, nothing else works → ③ Open “AI assistant” in the header and say, e.g., “Add a host 10.0.0.12 for me”—credentials, hosts, tags, batch jobs, and tasks can be handled in natural language; ④ (Optional) you can also use the “Host management” menu and build each item by hand.

One principle: model-assisted chat is the core way to work in this system; you start from conversation. See the README and docs/ directory, or click “Help” in the top-right after you sign in.

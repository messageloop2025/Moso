# 毛竹 综合操作手册与实战方法

本文档面向日常使用者，尽量用“先理解、再操作、再排障”的方式，系统说明 毛竹 中各功能的技术边界、推荐方法与常见流程。若只想快速查某个主题，可先看 [index.md](index.md) 再跳转到对应帮助页。

---

## 1. 系统的工作方式

毛竹 本质上由 4 层能力组成：

1. **资源层**：主机、凭证、分组、维护历史、最佳实践、帮助文档。
2. **执行层**：SSH 命令、SSH 终端、批量任务、文件上传、本机管理。
3. **AI 协同层**：AI 助手、主机详情 AI、本机管理 AI、会话级提示词、主机知识。
4. **知识层**：`web/aihelp` 帮助文档、最佳实践、按主机保存的 AI 知识。

理解这 4 层后，很多操作都会更清晰：

- **主机** 是 AI 和批量任务的执行对象。
- **凭证** 决定系统如何登录主机。
- **分组** 决定如何组织服务器树与批量范围。
- **控制台** 决定 AI 是否能进行连续交互式操作。
- **主机知识** 决定 AI 是否知道该主机上的账户、密码、路径、服务目录等。
- **最佳实践** 决定 AI 在安装、部署、排障前是否有推荐方法可参考。
- **帮助文档** 决定用户和 AI 如何理解系统本身怎么用。

## 2. 推荐的使用顺序

对于第一次接触系统的用户，建议按下面顺序使用：

1. 先创建 **凭证**。
2. 再创建 **主机** 并绑定凭证。
3. 用单机命令或控制台确认 SSH 连通。
4. 按业务或环境创建 **主机分组**。
5. 需要复用脚本时，把脚本放到 `web/fs`。
6. 需要自然语言协作时，再使用 **AI 助手** 或 **主机详情 AI**。
7. 需要多机并行时，再使用 **批量任务** 或让 AI 创建多个 AI 控制台协作。

这样做的好处是：

- 先确认连接，再做自动化，能明显减少排障成本。
- 先整理分组和文件，再做批量下发，效率更高。
- 先补充主机知识，再让 AI 执行需要密码、路径、服务信息的任务，成功率更高。
- 需要 AI 分析合同、报表、幻灯片等时，可在会话中上传 **PDF / Office** 附件；长回复会在流式过程中对表格、代码块等**分块排版**（见 [ai-assistant.md](ai-assistant.md)）。

## 3. 主机、凭证与分组的关系

### 3.1 主机

每台主机至少需要：

- 名称
- IP 或域名
- SSH 端口
- 一个可用凭证

若主机无法连接，优先检查：

- IP / 域名是否正确
- 端口是否开放
- SSH 服务是否启动
- 账号、密码、私钥是否正确
- 防火墙、安全组、路由是否允许访问

### 3.2 凭证

系统将 **凭证** 与 **主机** 分离，目的是复用与统一维护。

适用方法：

- 多台服务器使用同一账号时，复用一条凭证即可。
- 账号密码变更时，只改凭证，不必逐台改主机。
- 建议用“环境 + 账号用途”命名凭证，如“生产-root”“测试-deploy”。

### 3.3 分组与服务器树

推荐按以下思路建树：

- 按环境：生产 / 测试 / 开发
- 按业务：网关 / Web / API / DB / 缓存
- 按地域：华东 / 华南 / 香港 / 海外
- 按归属：团队 A / 团队 B / 外部客户

建议：

- 分组层级不要太深，2 到 4 层通常足够。
- 一个分组尽量表达单一维度，避免“生产-华东-支付-Web-临时”这类过长命名。
- 批量任务前，先保证分组结构准确，否则容易误选主机。
- 在 **服务器树** 页面可用 **右键 →「添加分组」** 快速建组：在分组上添加为 **子分组**；在 **未分组** 区域（非主机行）或 **空白处** 添加为 **顶级分组**（界面中英文菜单项一致）。

## 4. SSH 控制台的使用理念

毛竹 中的 SSH 控制台适合做 **连续的、交互式的、需要观察输出过程** 的任务，例如：

- 安装软件
- 执行需要多步确认的命令
- 输入 sudo 密码
- 实时查看日志
- 逐步排障

如果只是执行一条确定性的命令，通常直接用单次 SSH 执行更快。

### 4.1 用户控制台与 AI 控制台的区别

系统现在区分两类 SSH 控制台：

- **用户创建控制台**：由用户手动新建并连接，主要供用户自己操作。
- **AI 创建控制台**：由 AI 通过系统能力创建，主要供 AI 连续执行任务。

当前规则非常重要：

- AI **只能操作 AI 创建的 SSH 控制台**。
- AI **不能读取、切换、关闭、发送内容到用户创建的 SSH 控制台**。
- 如果当前界面激活的是 **用户控制台**，AI 不会因为自己要执行命令而强行切换界面。
- 如果当前激活的是 **AI 控制台**，AI 可以在多个 AI 控制台之间自动切换，以便并行执行任务。

这样设计的目的，是避免 AI 与用户互相抢占终端，打断用户手工操作。

### 4.2 什么时候适合让 AI 开多个控制台

适合场景：

- 一台主机上需要同时看日志和执行部署命令
- 多台主机之间需要对比状态
- 一个任务在等待安装/下载时，AI 可以切到另一个控制台继续工作
- 需要一边 tail 日志，一边执行修复命令

不适合场景：

- 用户正在手动敲命令的控制台
- 需要你人工确认每一步的高风险操作
- 容易混淆上下文的临时调试过程

### 4.3 推荐的终端使用方法

- 让 AI 做长任务时，明确要求“为这个任务新建 AI 控制台”。
- 让 AI 并行工作时，明确要求“日志一个控制台、部署一个控制台、巡检一个控制台”。
- 任务完成后，可让 AI 关闭不再需要的 AI 控制台，减少界面干扰。
- 如果你要接管控制台，请优先使用用户自己创建的控制台。

### 4.4 SSH 通道（ssh_channel）与「SSH通道管理」

除 Web 控制台外，AI 还可创建 **SSH 通道**（`ssh_channel_*` 工具）：后台 PTY 会话，适合安装、编译、sudo、嵌套 SSH 等**多步交互**，用户**不必**一直盯着 Web 终端。

- **查看输出**：AI 助手 / 主机 AI 左侧 **「SSH通道管理」** Tab → 只读 xterm +「刷新输出」/「实时监视」。
- **与控制台分工**：用户要**边看边敲** → Web 控制台；用户不必看界面、AI 后台跑流程 → ssh_channel。
- AI 在聊天里创建/关闭通道后，该 Tab 列表会自动更新。

详见 [ssh-channel.md](ssh-channel.md)。

## 5. AI 助手的三种工作模式

### 5.1 全局 AI 助手

适合：

- 查询有哪些主机、分组、凭证
- 跨主机排障
- 跨分组批量处理
- 归纳最佳实践
- 阅读帮助文档并回答“怎么用”

### 5.2 主机详情 AI

适合：

- 聚焦单台主机排障
- 对某台主机持续执行命令
- 记录这台主机的知识
- 结合该主机控制台做连续操作

### 5.3 本机管理 AI

适合管理员：

- 管理运行 毛竹 的本机
- 修改本机文件
- 查看本机日志
- 管理本机进程
- 做部署、备份、脚本调试

注意：

- 本机管理与远程主机管理是两套不同范围。
- `web/fs` 是每用户隔离目录；本机管理可访问更广的本机路径。

## 6. 会话级提示词怎么用

会话级提示词适合给 AI 加“本轮任务规则”，例如：

- 只做只读巡检，不修改配置
- 回复简洁，只给结论和命令
- 所有改动前先说明风险
- 禁止重启服务
- 优先使用 Ubuntu / Debian 命令风格

推荐写法：

- 写清楚目标：如“本会话只处理 Nginx 问题”
- 写清楚边界：如“不要安装新软件，不要改防火墙”
- 写清楚风格：如“先给计划，再执行”

不推荐写法：

- 太空泛，如“你要聪明一点”
- 太冲突，如“先不要执行”又“立刻自动修复”
- 混入大量历史日志，降低可读性

## 7. 主机知识怎么维护

主机知识是按主机保存的 AI 内部知识，适合记录：

- sudo 密码
- MySQL / Redis / MongoDB 账号
- 部署目录
- 日志目录
- 配置文件路径
- 服务名
- 容器名
- 项目启动命令

推荐记录格式：

```md
主机用途：支付 API 节点
登录用户：deploy
sudo：免密 sudo
项目目录：/data/apps/pay-api
配置文件：/data/apps/pay-api/.env
systemd 服务：pay-api.service
Nginx 配置：/etc/nginx/conf.d/pay-api.conf
日志目录：/data/logs/pay-api
备注：通过 Docker Compose 部署
```

建议：

- 用“键: 值”风格，方便 AI 抽取。
- 尽量记录“路径、服务名、端口、账号用途”。
- 用户一旦更改了部署结构，要及时更新主机知识。

## 8. 文件系统（web/fs）的最佳用法

`web/fs` 更像是你的“运维工作区”，适合放：

- Shell 脚本
- Python 脚本
- 配置模板
- 安装包
- 压缩包
- 导出的 Markdown
- 临时排障文件

建议目录结构：

```text
scripts/
configs/
packages/
backups/
exports/
temp/
```

推荐方法：

- `scripts/` 放部署和巡检脚本
- `configs/` 放 Nginx、systemd、应用配置模板
- `packages/` 放 `.tgz`、`.zip`、安装包
- `backups/` 放从主机拉回或本地备份的文件

适用流程：

1. 在 `web/fs` 中准备脚本或配置
2. 让 AI 检查内容是否正确
3. 上传到目标主机
4. 在目标主机执行
5. 成功后再沉淀到最佳实践或帮助文档

## 9. 批量任务适合做什么

批量任务适合 **同构、同步骤、低交互** 的场景，例如：

- 批量巡检磁盘、内存、CPU
- 批量检查服务状态
- 批量下发脚本
- 批量推配置
- 批量重启服务或机器

不太适合：

- 需要逐台人工判断的复杂故障
- 需要交互确认密码的过程
- 主机差异很大、命令不统一的环境

推荐做法：

- 先选小范围试跑
- 再扩到整组
- 高风险命令先让 AI 生成，再人工确认
- 把常用脚本放到 `web/fs`，避免每次手写

## 10. AI 助手中的图形化输出

系统聊天页已经支持图形化代码块的渲染与导出，适用于：

- 网络关系图
- 业务流程图
- 思维导图
- 柱状图、折线图、饼图等图表

建议用法：

- 让 AI 先给文本结论，再附图
- 图中节点名尽量短，避免移动端拥挤
- 图表颜色要和深色主题兼容
- 导出 PNG / SVG 前先确认图已正常渲染
- Mermaid 图渲染前会先做预检查与常见误写自动修复；若修复成功，系统会尽量把修复后的内容写回当前聊天历史，便于下次直接复用

适合表达的内容：

- 主机拓扑
- 服务依赖关系
- 发布流程
- 巡检结果汇总
- 故障原因分析路径

## 11. 维护历史与最佳实践怎么配合

两者用途不同：

- **维护历史**：记录“做过什么”
- **最佳实践**：总结“以后推荐怎么做”

推荐流程：

1. 执行一次真实维护
2. 将关键动作写入维护历史
3. 如果这次方法稳定可复用，再沉淀成最佳实践

例如：

- 维护历史记录“2026-03-12 修复 pay-api 证书过期”
- 最佳实践总结“Ubuntu + Nginx + Certbot 续期失败的排查方法”

## 12. 本机管理适合哪些管理员场景

本机管理更适合平台管理员而非普通运维用户，常见场景：

- 查看 毛竹 服务日志
- 修改部署配置
- 读写本机文件
- 启动和终止本机进程
- 调试脚本
- 管理上传目录、备份目录、静态文件

注意：

- 本机管理操作的不是远程主机，而是 毛竹 所在机器。
- 若不确定路径范围，先只读查看，再决定是否写入或删除。
- 删除、重命名、截断文件前，建议先备份。

## 13. 常见操作模板

### 13.1 新增一台 Linux 主机

1. 创建凭证
2. 新增主机并绑定凭证
3. 检测主机类型
4. 打开控制台或执行一条简单命令验证
5. 补充主机知识
6. 放入合适分组

### 13.2 用 AI 部署一个项目

1. 在主机详情 AI 中打开该主机
2. 补充项目目录、服务名、配置路径到主机知识
3. 在 `web/fs` 中准备脚本或压缩包
4. 让 AI 检查部署方案
5. 必要时让 AI 新建多个 AI 控制台并行处理
6. 完成后记录维护历史

### 13.3 批量巡检一组主机

1. 确认分组无误
2. 先对 1 到 2 台主机试跑命令
3. 再创建整组批量任务
4. 检查失败项
5. 对失败项重试或单机排障

### 13.4 排查服务异常

1. 先确认主机是否可连
2. 查看服务状态
3. 查看日志
4. 查看端口监听
5. 查看配置文件
6. 如需修复，再执行变更
7. 最后记录维护历史

## 14. 常见风险与避免方法

### 14.1 误操作生产环境

避免方法：

- 按环境分组
- 主机命名中带环境标识
- 会话级提示词中写明“当前仅限测试环境”
- 批量任务前先小范围试跑

### 14.2 AI 使用了错误终端

现在系统已限制 AI 只操作 AI 创建的终端，但仍建议：

- 用户手工操作时使用用户终端
- AI 自动化任务时使用 AI 终端
- 多任务并行时给 AI 明确说明每个终端的用途

### 14.3 路径、权限、账号信息不明确

避免方法：

- 补充主机知识
- 在帮助文档中沉淀规范
- 将通用经验沉淀为最佳实践

### 14.4 批量任务放大错误

避免方法：

- 先试一台
- 再试一组
- 最后全量
- 对高风险动作要求 AI 先给计划再执行

## 15. 遇到问题时的排查顺序

### 15.1 连不上主机

依次检查：

- 主机地址
- SSH 端口
- SSH 服务是否启动
- 凭证是否正确
- 防火墙 / 安全组
- 是否被目标主机拒绝

### 15.2 AI 不能继续操作终端

依次检查：

- 当前聊天区域是否已有 AI 创建终端
- 终端是否已连接
- 当前是否切到用户终端
- 是否被手动关闭
- 是否需要 AI 重新创建控制台

### 15.3 文件上传失败

依次检查：

- `web/fs` 路径是否正确
- 目标主机路径是否可写
- 目标目录是否存在
- 登录账号是否有权限
- 磁盘空间是否足够

### 15.4 批量任务失败较多

依次检查：

- 分组选择是否正确
- 主机凭证是否一致有效
- 命令是否适用于所有目标主机
- 是否存在系统类型差异
- 是否有网络连通性问题

## 16. 如何持续完善系统知识

推荐把知识沉淀到 3 个地方：

1. **主机知识**：主机私有、偏运行细节
2. **最佳实践**：方法论、偏通用经验
3. **aihelp 文档**：给用户看的系统使用说明

推荐原则：

- 这台主机独有的信息，写到主机知识
- 多次复用的技术方案，写到最佳实践
- “系统怎么用”的说明，写到 aihelp

## 17. 建议的文档维护方式

管理员维护帮助文档时，建议：

- 每新增一个新能力，就补一页或补一个章节
- 每次规则变化后，同步更新帮助文档
- 文档标题尽量面向用户，而不是面向代码
- 在 `index.md` 中保持目录完整

如果你是普通用户，也可以直接问 AI：

- “这个系统里我应该怎么做批量发布？”
- “主机详情 AI 和 AI 助手有什么区别？”
- “什么时候该用控制台，什么时候该用单次命令？”
- “如何让 AI 只处理当前主机，不碰别的机器？”

AI 会读取帮助文档后再回答。

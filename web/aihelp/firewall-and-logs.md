# Linux 防火墙与系统日志专题手册

这份文档面向 Linux 主机上的两类常见任务：

- **防火墙与端口规则**
- **系统日志与服务日志检查**

它适合在你已经把 Linux 主机接入 毛竹 后，用来指导排障、加固、放行端口和查看日志。

---

## 1. 什么时候用这份文档

适合场景：

- 端口开不通
- 想开放或关闭某个端口
- 想做 DNAT / 端口转发
- 想确认当前主机暴露了哪些端口
- 想查系统报错、服务报错、登录失败
- 想定位 Nginx、SSH、内核或业务进程异常

---

## 2. 推荐排查顺序

遇到网络或服务问题时，推荐按这个顺序看：

1. 服务是否在运行
2. 端口是否在监听
3. 防火墙是否放行
4. 相关日志里有没有报错

如果顺序反过来，往往会浪费很多时间。

---

## 3. Linux 防火墙：先理解你在做什么

Linux 防火墙相关操作通常包括：

- 开放端口
- 关闭端口
- 查看已有规则
- 做 DNAT 转发
- 保存和重载规则

### 常见目标

- 开放 Web 端口
- 开放 SSH 端口
- 开放 WireGuard 端口
- 把公网端口转发到内网服务

---

## 4. 先判断主机使用哪种防火墙体系

不同 Linux 发行版的防火墙方式可能不同，常见有：

- `iptables`
- `nftables`
- `firewalld`

### 一般理解

- `iptables`：较传统
- `nftables`：较新
- `firewalld`：在一些发行版里更常见，带 zone 和服务概念

### 推荐做法

不要一上来就硬写命令，先确认当前系统主要用哪套工具。

---

## 5. 场景一：查看当前开放了哪些端口

这是最基础、也最常见的动作。

### 推荐步骤

1. 先看监听端口
2. 再看防火墙规则
3. 对比服务和规则是否一致

### 常见命令

```bash
ss -tlnp
iptables -L -n
nft list ruleset
firewall-cmd --list-all
```

### 你通常在找什么

- 服务是否真的监听了目标端口
- 防火墙是否真的放行了该端口
- 是否只监听了本地地址而不是外部地址

---

## 6. 场景二：开放一个端口

适合：

- 新部署了 Web 服务
- 新增了 API 服务
- 开放 SSH / WireGuard / 数据库端口

### 推荐步骤

1. 先确认服务已在监听
2. 再确认要开放的是 TCP 还是 UDP
3. 再添加防火墙规则
4. 再重载或保存规则
5. 最后从外部验证端口是否可达

### 常见方式

`firewalld` 示例：

```bash
firewall-cmd --add-port=80/tcp --permanent
firewall-cmd --reload
```

### 注意

- 不要开放不必要的端口
- 生产环境开放端口前先确认暴露范围

---

## 7. 场景三：关闭一个端口

适合：

- 服务下线
- 端口误暴露
- 临时调试结束
- 安全加固

### 推荐步骤

1. 先确认是否还有服务依赖该端口
2. 再移除防火墙规则
3. 再验证外部访问是否已失效

### 注意

- 关闭 SSH 端口前要特别谨慎
- 若机器只靠 SSH 管理，错误关端口可能导致失联

---

## 8. 场景四：做 DNAT / 端口转发

DNAT 适合把访问本机某端口的流量转到另一台机器或另一端口。

### 典型场景

- 公网 `80` 转内网 `8080`
- 公网入口机转发到内网业务机
- 端口映射

### 推荐步骤

1. 先确认源端口和目标地址
2. 再确认目标服务本身可达
3. 配置 DNAT 规则
4. 必要时加 SNAT / masquerade
5. 验证转发是否生效

### 特别提醒

- DNAT 问题通常不只在一条规则，可能还涉及路由、回程流量、防火墙策略
- 不要只改 PREROUTING 就结束，往往还要检查 FORWARD 和 NAT 相关配置

---

## 9. 场景五：保存与持久化规则

很多人只改了规则，却忘了持久化，重启后规则就丢了。

### 推荐步骤

1. 先确认规则在当前会话已生效
2. 再按当前防火墙体系做持久化
3. 必要时重载服务
4. 再做一次验证

### 常见方式

- `iptables-save`
- `iptables-restore`
- `firewall-cmd --reload`
- `nft -f 配置文件`

---

## 10. 日志检查：先知道该查哪类日志

Linux 日志通常分几类：

- `journalctl` / systemd 日志
- `/var/log` 下的传统日志
- 应用日志
- Nginx / SSH / 认证日志
- 内核日志

### 建议

不要一开始就全盘翻日志，先明确你在查：

- 登录问题
- 服务问题
- 网络问题
- 配置问题
- 内核或硬件问题

---

## 11. 场景六：查看最近的服务日志

适合：

- 服务启动失败
- 服务重启后不正常
- 想确认最近一次报错

### 推荐步骤

1. 先明确服务名
2. 再查看最近日志
3. 再缩小到具体时间范围

### 常见命令

```bash
journalctl -u 服务名 -n 100
journalctl -b
journalctl -f
```

### 你通常在找什么

- 启动失败信息
- 配置语法错误
- 权限不足
- 依赖项不存在

---

## 12. 场景七：按时间或级别筛选日志

当日志很多时，必须缩小范围。

### 常见做法

```bash
journalctl --since "1 hour ago"
journalctl -p err
```

### 推荐场景

- 查“今天下午”的报错
- 查“最近一小时”的异常
- 只看 error 级别

这样更适合让 AI 帮你快速定位关键行。

---

## 13. 场景八：查看 SSH / 登录相关日志

适合：

- 登录失败
- sudo 失败
- 可疑登录
- SSH 配置变更后无法访问

### 常见位置

- `journalctl -u sshd`
- `/var/log/auth.log`（Debian / Ubuntu）
- `/var/log/secure`（RHEL 系）

### 推荐步骤

1. 先看最近登录失败时间点
2. 再看对应日志
3. 判断是密码错、权限错，还是 SSH 服务本身问题

---

## 14. 场景九：查看 Nginx 或应用日志

适合：

- 502 / 504 / 404
- 请求异常
- 访问流量问题
- 代理转发异常

### 常见位置

- `/var/log/nginx/access.log`
- `/var/log/nginx/error.log`
- 应用自己的日志目录

### 推荐步骤

1. 先看错误日志
2. 再看访问日志
3. 最后结合时间点和请求特征分析

---

## 15. 场景十：查看内核与硬件日志

适合：

- 磁盘报错
- 驱动问题
- 内核异常
- 系统级故障

### 常见命令

```bash
journalctl -k
dmesg
```

### 建议

- 硬件相关问题优先看内核日志
- 与服务本身无关的异常，不要只盯着应用日志

---

## 16. AI 如何配合这类任务

你可以直接让 AI：

- 查当前开放端口
- 分析为什么端口不通
- 解释某段日志
- 只筛出错误日志
- 给出开放端口或 DNAT 的建议命令

### 推荐提问方式

- “检查这台机器 8080 为什么外部访问不到。”
- “看 nginx 最近 100 行错误日志并总结原因。”
- “只查看最近 1 小时的 SSH 登录失败记录。”
- “先只读分析，不要直接修改防火墙规则。”

---

## 17. 常见问题

### 17.1 端口开了还是不通

优先检查：

- 服务是否真的监听
- 防火墙是否真的放行
- 云安全组或上游网络是否拦截
- 服务是否只绑定到 `127.0.0.1`

### 17.2 日志太多看不过来

建议：

1. 先按时间缩小
2. 再按服务缩小
3. 再按错误级别缩小

### 17.3 做了防火墙修改后服务还是异常

说明问题不一定在防火墙本身，还可能在：

- 服务未启动
- 监听地址错误
- 代理链路错误
- DNAT / 路由 / 回程流量问题

---

## 18. 推荐的使用习惯

- 先看服务，再看端口，再看防火墙，再看日志
- 修改防火墙前先做只读检查
- 高风险规则先小范围验证
- 日志排查要按时间和服务收敛
- 重要排障过程记得写维护历史
